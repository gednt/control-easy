# Requirements — Modernization Roadmap

> Spec folder: `.specs/modernization-roadmap/`
> Goal: Move the legacy **ControlEasy 5** (WPF / .NET Framework 4.8 / MySQL) desktop application to a modular, web-based, containerized platform whose data-access layer is built on top of [`DBTools_SQL`](https://github.com/gednt/DBTools_SQL) (LINQ-first, multi-provider).

## User Stories

### Architecture & Migration Strategy
- **UC-1:** As a *product owner*, I want a phased migration plan (Strangler Fig) so the legacy WPF app keeps working while the web app replaces it screen by screen, with no big-bang rewrite.
- **UC-2:** As an *architect*, I want the new system to be a **modular monolith** with Clean Architecture inside each module so we can ship a single deployable today and split into microservices later without rewriting domain code.
- **UC-3:** As a *developer*, I want a consistent module template (`Domain → Application → Infrastructure → Api`) so new features (Residents, Visits, Vehicles, Service Providers, Apartments, Gatehouse) follow the same structure.

### Frontend
- **UC-4:** As a *doorman (porteiro)*, I want a modern, responsive web UI (Angular 18+ SPA with Angular Material) that I can use from a tablet or a phone, replacing the WPF window that only runs on Windows desktops. Visual contract and reference: see `.specs/2 - visual-design-system/`, the Penpot library + token contract at `docs/penpot/`, and the build-free prototype at `mockup/` (smoke-tested via `mockup/SMOKE.md`); the canonical home for these references in this spec is **design.md → Design system & visual prototype**.
- **UC-5:** As a *resident (morador)*, I want the web UI to load fast (lazy-loaded feature modules, OnPush change detection, signals) and to be served as a static bundle behind nginx so the gatehouse is not blocked when the network is slow. Visual contract and reference: see `.specs/2 - visual-design-system/`, the Penpot library + token contract at `docs/penpot/`, and the build-free prototype at `mockup/` (smoke-tested via `mockup/SMOKE.md`); the canonical home for these references in this spec is **design.md → Design system & visual prototype**.
- **UC-6:** As an *administrator*, I want the web app to be served over HTTPS and proxied by a single reverse proxy so deployments are simple and TLS is centralized. Visual contract and reference: see `.specs/2 - visual-design-system/`, the Penpot library + token contract at `docs/penpot/`, and the build-free prototype at `mockup/` (smoke-tested via `mockup/SMOKE.md`); the canonical home for these references in this spec is **design.md → Design system & visual prototype**.

### Frontend
- **UC-7:** As a *frontend developer*, I want a versioned REST API (`/api/v1/...`) returning JSON with `ProblemDetails` errors and an OpenAPI spec so I can auto-generate the Angular TypeScript DTOs/interfaces with `ng-openapi-gen`.
- **UC-8:** As a *backend developer*, I want dependency injection, structured logging, and centralized exception handling pre-wired in `Program.cs` so each new endpoint is one-liner.
- **UC-9 (updated):** As a *security officer*, I want JWT bearer authentication with role-based authorization so the same API serves all user types safely. The role set is: `PlatformAdmin` (platform-wide, provisioned at first boot), `TenantAdmin` (per-tenant, created by `PlatformAdmin`), `Morador` (per-tenant resident), and zero or more `AttendantProfile` rows per tenant (per-tenant attendant assignment carrying its own permission set). The JWT carries claims: `sub` (UserId), `tenant_id` (GUID, present for all non-`PlatformAdmin` calls), `profile_id` (AttendantProfileId, present for attendant sessions), `roles[]` (sourced from the active profile, e.g. `["Attendant"]` or `["TenantAdmin"]`).

### Data Access (DBTools_SQL)
- **UC-10:** As a *backend developer*, I want **all** database reads and writes expressed with `LinqHelper<T>` / `Linq<T>` lambdas (`Where`, `WhereEquals`, `WhereContains`, `InnerJoin`, etc.) so queries are type-safe and SQL is generated by the library.
- **UC-11:** As a *DBA*, I want the data-access layer to be **provider-agnostic** (MySQL today, PostgreSQL/SQL Server tomorrow) by changing one config value, with no code changes.
- **UC-12:** As a *security officer*, I want every query to be **parameterized** automatically (DBTools_SQL's `SqlValidator` + `DbParameter`) so SQL injection is structurally impossible.
- **UC-13:** As a *developer*, I want `Linq<T>.AsQueryable()` for deferred, SQL-translated IQueryable queries in paged/filtered list endpoints so I don't load entire tables into memory.

### Containerization
- **UC-14:** As a *DevOps engineer*, I want a `docker-compose.yml` that starts the whole stack (`api`, `web`, `db`, `reverse-proxy`, `adminer`) with one command so local dev = production.
- **UC-15:** As a *DevOps engineer*, I want multi-stage Dockerfiles (build → runtime) so images are small and the SDK is not shipped to production.
- **UC-16:** As a *security officer*, I want secrets (DB password, JWT signing key) injected via environment variables / Docker secrets — not committed in `App.config`.

### Dependency Management
- **UC-17:** As a *developer*, I want **Central Package Management** (`Directory.Packages.props`) with pinned versions so all modules share the same package versions.
- **UC-18:** As a *DevOps engineer*, I want NuGet packages restored **inside** Docker (via layer-cached `csproj` restore step) so CI is fast and reproducible.

### Phased Migration
- **UC-19:** As a *product owner*, I want a **4-phase roadmap** (Foundation → Strangler Pilot → Module Migrations → Legacy Decommission) with explicit go/no-go gates between phases.
- **UC-20:** As a *QA*, I want integration tests that run against a real MySQL container (Testcontainers) so the migration is verified end-to-end, not just mocked.

### Multi-Tenancy & Attendant Profiles
- **UC-21:** As a *platform operator*, I want the system to host many condominiums (tenants) on a single deployment with strict data isolation so one tenant can never read or write another tenant's data, even through a bug in the API.
- **UC-22:** As a *platform operator*, I want every read and write in the data-access layer to carry an automatic `tenant_id` filter (a global query filter) so application code cannot accidentally bypass tenant isolation.
- **UC-23:** As a *platform operator*, I want a `PlatformAdmin` role that can create, suspend, and resume tenants, and a `TenantAdmin` role that is scoped to a single tenant, so onboarding and administration are self-service and auditable.
- **UC-24:** As a *tenant administrator*, I want one or more **attendant profiles** (`AttendantProfile`) per attendant — each with a shift, a gatehouse assignment, an `Active` flag, and a permission set — so a condominium with several door attendants can be modeled accurately instead of a single global `Porteiro` role.
- **UC-25:** As a *tenant administrator*, I want a shift schedule (`Shifts` lookup: name, start time, end time, crosses-midnight) and a gatehouse lookup (`Gatehouses`: name, location) so attendant profiles are bound to a real, manageable schedule and physical entry point.

---

## Out of Scope (for this roadmap)
- Migrating data from the existing `controlEasyDB.db` to a new schema (handled in a separate data-migration spec).
- Replacing the camera / facial-recognition integration (EmguCV) — to be redesigned in a later spec.
- Mobile-native apps (PWA / responsive web is sufficient for v1).
- Billing / subscription management (handled by an external billing system, not in this platform).
- Cross-tenant analytics (a `PlatformAdmin`-facing BI dashboard is a separate product).
