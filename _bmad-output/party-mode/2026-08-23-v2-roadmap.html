Design Principles

🎯
Logging is faster than skipping. The 3-second gatehouse workflow is the honesty enforcement. If logging takes longer than not logging, the porteiro will skip it.
📷
CCTV is the external backstop. ControlEasy carries timestamps; the condominium carries footage. The syndic cross-references by recorded_at.
⚖️
ControlEasy enables, doesn't enforce. The consent policy is the condominium's, not the software's. The software makes the policy operational.
🖼️
Client-side only for image processing. No server-side compression, thumbnailing, or EXIF stripping. Browser canvas does it all.
🚪
ControlEasy is a participant, not a gatekeeper. The door opens independently; the API observes and can trigger, but doesn't block physical access.
🧩
No speculative abstractions. IDeviceHandler emerges from the second real integration, not before it.
👁️
No approval workflow, no anomaly detection. v2.0 ships visibility. Let humans catch dishonesty with the tools they already have.

v2.0 — Gatehouse Photo & Consent Ledger

The porteiro captures a photo of anyone entering the condominium. The condominium sets a per-category consent policy. Every entry is logged with millisecond-precision timestamps cross-referenceable with external CCTV.

Phase 11: Photos & Consent Schema Infrastructure

Depends on: v1.1 (Phase 10) · Requirements: PHOTO-01 · Spec: .specs/photo-capture/
  • IStorageProvider (local + S3/MinIO)
  • photos table, consent_audit_log table, tenant_consent_policy table
  • Hard DB constraint: entered_with_consent → photo non-null
  • Permissions: photos.read / photos.write / photos.delete
  • Endpoints: POST/GET/DELETE /api/v1/photos
  • Append-only enforcement on consent_audit_log

Phase 12: Photo Capture & Display

Depends on: Phase 11 · Requirements: PHOTO-02 · Spec: .specs/photo-capture/ · UI: yes
  • ce-photo-capture: getUserMedia camera + file upload
  • Resize ≤1280px → JPEG ≤500KB (0.8 → 0.6 → floor 0.3)
  • EXIF strip via canvas redraw
  • 128×128 thumbnail client-side
  • Upload retry: 3 attempts, exponential backoff
  • ce-photo display: thumbnails in tables, lightbox detail
  • Integration: residents, visitors, vehicles, service providers

Phase 13: Consent Policy & Gatehouse Workflow

Depends on: Phase 12 · Requirements: CONSENT-01, CONSENT-02, CONSENT-03 · Spec: .specs/consent-gatehouse/ · UI: yes
  • Per-tenant per-category consent toggle (dwellers/visitors/service-providers/vehicles)
  • Four entry states (see matrix below)
  • 3-second gatehouse workflow — logging faster than skipping
  • Audit review UI: filter, override highlighting, CSV export
  • Millisecond-precision recorded_at for CCTV cross-reference

v2.1 — Door Integration (Optional)

Condominiums that opt in can integrate ControlEasy with their door relay and card/biometric readers. Gated on a real condominium with hardware.

Phase 14: Door Relay & Unlock Commands

Depends on: v2.0 + real hardware · Requirements: DOOR-01 · Spec: .specs/door-integration/
  • IDoorController abstraction (vendor-specific)
  • POST /api/v1/devices/{deviceId}/unlock — porteiro role, HMAC-SHA256 signed
  • Rate-limited (1 per 3s/device), audit-logged, tamper-evident
  • Tenant opt-in flag (default false)
  • Hardware fallback — door opens without API (card reader + manual release)
  • Event queue with replay on reconnect
  • Threat model document

Phase 15: Reader Events & Device Health

Depends on: Phase 14 + second integration · Requirements: DOOR-02, DOOR-03 · Spec: .specs/door-integration/
  • IDeviceHandler — from two real integrations, not speculative
  • DeviceEvent normalization (vendor-agnostic)
  • Card match → entered_with_consent; unknown → denied
  • device_events table with occurred_at vs processed_at
  • Device health: heartbeats, offline alerts, error rate thresholds
  • Health dashboard UI + porteiro alert toast
