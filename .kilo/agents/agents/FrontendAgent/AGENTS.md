# Project Overview

ControlEasy Reborn is the modernization of a legacy WPF/.NET Framework 4.8 condominium access-control application ("ControlEasy 5"). The target platform is a modular, web-based, containerized system with:

- **Frontend:** Angular 18+ SPA (standalone components, signals, TypeScript strict). Frontend work lives in this repo at `src/Web/ControlEasyReborn.Web` (planned in `.specs/1 - modernization-roadmap/tasks.md` task 1.8).
- **Backend:** ASP.NET Core 8 Web API in a modular monolith (`Modules/<Feature>/{Domain,Application,Infrastructure,Api}`).
- **Data:** MySQL 8, abstracted by the `DBTools_SQL` library (LINQ-first; `Linq<TModel>`, `IAsyncSqlClient`). **No EntityFramework, no MySql.Data.**
- **Auth:** JWT bearer. The frontend stores the token and attaches it via an `HttpInterceptor`.
- **API contract:** Swashbuckle on the API; Angular types generated by `ng-openapi-gen` from `/swagger/v1/swagger.json` on every build.
- **Migration pattern:** Strangler Fig — legacy WPF keeps running behind feature flags while the Angular SPA replaces screens one module at a time (Residents first, then Visits, Vehicles, ServiceProviders, Administration, etc.).
- **Primary user roles (current scope):** `PlatformAdmin`, `TenantAdmin`, `Morador` (resident), `AttendantProfile` (per-tenant gatehouse attendant).
- **Key entities:** Residents, Apartments, Vehicles, Visits (visitantes + fluxo/portaria), Service Providers, Audit log, Tenants.

The current repo state is **greenfield** (no Angular app, no backend code yet — only `AGENTS.md`, `README.md`, `.gitignore`, and `.specs/1 - modernization-roadmap/`). The half-started Blazor Server `.NET 5` prototype (`ControlEasy5/ControlEasyWeb/`) is scheduled for deletion in Phase 0, task 0.3.

# Technical details

## Stack (Angular side, as planned)

- **Framework:** Angular 18+, standalone components, signals for local/global state, `@if` / `@for` control flow, no NgModules.
- **Language:** TypeScript with `strict: true`, `noUncheckedIndexedAccess: true`, `exactOptionalPropertyTypes: true`.
- **Styling:** **Tailwind CSS v4** with the `@theme` directive and CSS custom properties (light + `[data-theme=dark]`). **Angular CDK** (overlay, a11y, dialog, menu) for headless behavior. **No Angular Material** — see open conflict in `.specs/2 - visual-design-system/`.
- **HTTP:** `HttpClient` + functional `HttpInterceptor` for JWT.
- **Forms:** Reactive Forms (`@angular/forms`).
- **Routing:** Lazy-loaded feature routes per module; `provideRouter` with `withComponentInputBinding`.
- **Generated types:** `ng-openapi-gen` consumed by a `prebuild` script; generated files committed (decision: yes — keeps builds deterministic and PR-reviewable; will be revisited if drift becomes painful).
- **Maps:** Leaflet (matches reference app).
- **Icons:** Lucide (open-source, tree-shakeable, matches the line-style iconography of the reference).
- **Charts:** Recharts (if/when a module needs them — not part of the design system).
- **i18n:** Not required for v1; structure routes/views so Angular `@angular/localize` can be added later.
- **Testing:** Jasmine + Karma for unit, Playwright for E2E (matches task 3.7).
- **Build/serve:** Angular CLI (`ng serve`, `ng build`); `proxy.conf.json` forwards `/api` to `https://localhost/api` in dev.
- **Linting:** ESLint (`@angular-eslint`) + Prettier.

## Naming conventions

- Files: `kebab-case.component.ts`, `kebab-case.service.ts`, `kebab-case.tokens.css`.
- Classes: `PascalCase` (`ButtonComponent`, `ThemeService`).
- Selectors: `ce-button`, `ce-card`, `ce-input`, `ce-stat-tile`, `ce-badge`, `ce-modal`, `ce-toast`, `ce-table`, `ce-empty-state`, `ce-spinner`, `ce-avatar`, `ce-tabs`, `ce-dropdown`, `ce-tooltip`, `ce-pagination`, `ce-breadcrumbs`. The `ce-` prefix avoids clashing with native elements and other libraries.
- Inputs/Outputs: `variant`, `size`, `disabled`, `loading` as enum-like string union inputs; outputs use the `change` / `dismiss` / `select` suffix pattern.
- Standalone components by default; `changeDetection: OnPush`.
- No NgModules in the application code (AppConfig + providers only).

# Strategy

For each implementation, generate a folder with the implementation name in the format `.specs/function-or-bug-fix`, each folder will have the name of the function or bug fix it intends to achieve.
- Inside it, you will generate three documents:
    - **Requirements:** What needs to happen, in the format of user story:
        - **UC[Number]:** As a user, I want/need to [what needs to happen or needs to be fixed]
    - **Conditional**:
        - If a feature:
            - **design.md:** How it will be done.
                - **Overview**: The context of the task being achieved. A concise three paragraphs introduction to the task.
                - **Glossary**: The naming conventions encountered or useful for the task execution. All the terms the agent will need to keep in the context while executing the plan.
                - **Architecture:**
                    - A Brief paragraph describing the architecture of the design of the feature.
                    - Titles with mermaid diagrams, flow, success criteria, components, files to be created, code snippets, testing strategy, verification approach, etc... Everything the design needs to be achieved... More items can be added as needed.
                        - Each item will be a title or subtitle.
                - **UI/UX Specification**:
                    - Component hierarchy and composition
                    - Layout diagrams and responsive behavior
                    - Interaction patterns (hover, focus, loading, error, empty states)
                    - Accessibility requirements (ARIA roles, keyboard navigation, screen reader announcements)
                    - Animation and transition specifications
        - If a bug:
            - **bugfix.md**:
                 - **Overview**: The context of the task being achieved. A concise three paragraphs introduction to the task.
                - **Glossary**: The naming conventions encountered or useful for the task execution. All the terms the agent will need to keep in the context while executing the plan.
                - **Bug details**: What is the anomaly?
                - **Bug condition**: This bug manifests when... [details]
                - **Examples:** Examples of the bug occurrence.
                - **Reproduction steps**: Step-by-step instructions to reproduce in the browser
                - **Unchanged behaviors**
                - **Fix Implementation**
                    - Assuming our root analysis is correct:
                        - Implementation description
        - **tasks.md**: Step by step implementation with verification gates of the previous files. The tasks itself.
            - [ ] 1. Task
            - [ ] 2. Task
            - [ ] 3. Task
            - [ ] etc...
            - Each task can have as many subtasks as needed.
            - ## Task Dependency Graph
            ```json
            {
              "waves": [
                { "wave": 1, "tasks": ["<task_id>", "..."] },
                { "wave": 2, "tasks": ["<task_id>", "..."] }
            ```

            Task IDs reference the numbered tasks above. Tasks in the same wave have no dependencies on each other and can run in parallel. A wave only starts after all tasks in the previous wave are complete. Add as many waves as the task complexity demands.
        - After the conclusion of any task is completed, mark it as done.

## Frontend-Specific Rules

- **Component-first design**: Every piece of UI must be decomposed into reusable, composable components before implementation begins.
- **Accessibility audit**: All implemented UI must meet WCAG 2.1 AA at minimum. Include ARIA attributes, keyboard navigation, and focus management in every component spec.
- **Responsive by default**: All layouts must be designed mobile-first. Breakpoints and adaptive behavior must be documented in design.md.
- **State locality principle**: Prefer local component state. Only elevate state to global stores when data is shared across distant components or needs to persist across routes.
- **Visual regression verification**: After implementing any UI change, capture a screenshot or snapshot and compare against the expected output.

You MUST use Chrome (via the Playwright browser tools) to verify work that can be observed in a browser — this applies to all cases, not just UX/UI changes:
